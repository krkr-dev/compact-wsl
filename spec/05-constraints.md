# 05. 動作環境と制約

## 動作環境

| 項目 | 条件 |
|---|---|
| OS | Windows 11（Windows 標準の `powershell.exe`、`diskpart`、`wsl.exe` を使う） |
| WSL | WSL2。`wsl.exe --list --running --quiet` と `wsl.exe --shutdown` が使える版 |
| VS Code | 1.100 以上 |
| 権限 | 表示と swap 削除は一般ユーザーで可。圧縮には管理者権限（UAC で昇格できること） |
| 拡張の導入先 | Windows 側（ローカル）。WSL 側に入れると動かない |

## 制約

- **削除と圧縮は、WSL に接続していない Windows 側のウィンドウからだけ実行できる。** WSL のウィンドウ自体が WSL クライアントになり、止めた直後に WSL を起動し直してしまうため
- **WSL クライアント（VS Code の WSL ウィンドウ、Windows Terminal の WSL タブ、Docker Desktop など）がある間は、削除と圧縮を中断する。** 利用者がそれらを閉じる必要がある
- **削除と圧縮では、WSL のすべてのディストロが停止する。** WSL2 のディストロは 1 つの VM を共有しているため
- **圧縮するのは対象ディストロの vhdx だけ。** 他のディストロは圧縮しない（swap.vhdx の削除と停止はすべてに及ぶ）
- **スパース vhdx には未対応。** `wsl --manage <distro> --set-sparse true` や `.wslconfig` の `sparseVhd=true` でスパースにした vhdx は、diskpart で圧縮できない見込み（未検証）。その場合は diskpart の失敗として通知される
- **WSL1 のディストロは対象外。** vhdx を持たないため
- **fstrim は、対象ディストロが起動中のときだけ実行する。** 停止中のまま圧縮した場合、以前に fstrim されていない削除済みの領域は縮まない
- **「取り戻せる見込み」は上限の目安。** `df` の使用量に ext4 の管理情報が含まれないため、実際に縮む量はこれより少ない
- **VS Code を閉じている間は、サイズを監視しない。**

## 既知の制限

- VS Code の WSL ウィンドウの判定は、`wsl.exe` のコマンドラインに `.vscode-server` が含まれるかどうかによる。VS Code の Remote - WSL の実装が変わると、「その他」として数えられる可能性がある（中断はされるので安全側）
- diskpart の処理中に VS Code を閉じた場合、diskpart は最後まで動くが、結果は通知されない。結果は `%TEMP%\compact-wsl\diskpart.log` に残る

## 安全対策

| リスク | 対策 |
|---|---|
| 作業中の内容が失われる | 実行前に確認ダイアログを出す。WSL のウィンドウを勝手に閉じない |
| 圧縮中に WSL が起動して vhdx が壊れる | WSL クライアントがあれば中断する。圧縮の直前にもう一度止まっていることを確かめる。diskpart は vhdx を読み取り専用でアタッチし、アタッチ中は WSL がその vhdx を使えない |
| vhdx がアタッチされたまま残る | 失敗したときに `detach vdisk` を実行する |
| 初回の圧縮で問題が起きる | 初回だけ `wsl --export` によるバックアップを勧める |
| 管理者権限の範囲が広がる | 管理者として実行するのは diskpart のバッチだけ。独自の実行ファイル（exe）は使わない |
| 言語によって判定がずれる | 言語で変わる出力は解析せず、終了コード、`--quiet` の出力、JSON だけで判定する |
